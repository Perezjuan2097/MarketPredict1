# Fase 2B.2 · Emisiones de pronósticos y base empresarial

## Contrato de emisión y guardado

1. `GET /api/models/<ticker>?horizon=5` conserva los campos existentes y añade `emission` con `id`, `expires_at` y `token`. Cuando no hay un lote guardable, `emission` es nulo. La consulta puede usar la caché interna del motor. La respuesta indica `Cache-Control: no-store` para evitar reutilizar un token desde un caché HTTP.
2. El servidor fija la identidad como SHA-256 del contenido canónico del lote, incluida su caducidad. La firma HMAC-SHA-256 usa la clave de aplicación existente y un propósito específico. El token contiene pronósticos válidos, consenso si existe, precios, retornos, rangos, pesos del consenso y procedencia del motor (parámetros, versiones, semilla, fuente y cortes). Es una firma de integridad y no un mecanismo de cifrado. No contiene identificadores de cuenta ni secretos.
3. La caducidad es el primero de estos instantes: una hora desde el corte, el límite temporal de la emisión y el cierre objetivo. El navegador conserva el token de la respuesta que presentó. Exige coincidencia con el activo y horizonte seleccionados antes de enviar `POST /api/me/predictions/from-models` con `{"emission_token":"..."}`, sesión y CSRF. El servidor verifica la firma y toma usuario exclusivamente de la sesión. No llama al motor ni al proveedor al guardar.
4. La clave persistente `(user_id, emission_id)` distingue las copias privadas por cuenta. La emisión contiene un resultado público, por lo que dos usuarios autenticados pueden guardar sus propias copias de la misma emisión sin poder leer ni cambiar las copias del otro. Una transacción inserta el registro de idempotencia, resuelve o crea el activo, crea todas las predicciones y vincula sus IDs en el orden original. Cualquier excepción revierte el lote, incluso el activo si fue creado en la operación. La restricción única arbitra concurrencia entre conexiones y procesos.
5. El código de respuesta exitoso permanece en 201 con `saved`. La repetición devuelve las filas ya existentes en su orden, con el estado vigente si fueron evaluadas o invalidadas. Una emisión vencida admite recuperar una copia ya guardada y devuelve 409 si el usuario aún no la guardó. Un token ausente o inválido devuelve 400. El endpoint protegido conserva sesión, propiedad, CSRF y predicciones privadas.

El envío antiguo de sólo símbolo y horizonte requiere actualizar el cliente porque no identifica una emisión verificable. El navegador actualizado obtiene el token del GET. El historial JSON de Seguimiento, la publicación manual, la evaluación posterior y las rutas públicas mantienen sus flujos respectivos. El guardado SQL mantiene las escalas de columnas existentes y conserva los valores emitidos en el JSON de procedencia de cada fila. No se archivan barras originales ni pesos internos de los estimadores.

## Migración y operación

`20261118_forecast_saves`, sucesora de `20261117_auth_sessions`, añade únicamente `forecast_emission_saves` y habilita RLS en PostgreSQL. No altera las predicciones existentes ni requiere poblar datos previos. Un esquema inicializado por ORM puede contener la tabla; la migración exige sus columnas y claves antes de aceptar ese estado. En SQLite se requiere una versión con UPSERT y RETURNING (3.35+). El repositorio en memoria es sólo para prueba/desarrollo y su idempotencia dura lo que el proceso.

Para una futura intervención, inspeccionar `alembic current`, confirmar la revisión base y ensayar sobre copia aislada. Con respaldo y autorización aparte, aplicar `python -m alembic upgrade 20261118_forecast_saves` antes de activar el código nuevo. Verificar revisión, clave compuesta, FK a usuarios, RLS y compatibilidad del rol actual de la aplicación. Conservar la tabla al revertir la aplicación. El downgrade destructivo no está habilitado.

Las réplicas deben usar la misma clave existente de la aplicación. Rotarla invalida los tokens emitidos incluso si los lotes guardados permanecen en SQL. La tabla conserva IDs y crece con los lotes guardados; cualquier futura regla de borrado de predicciones debe gestionar el registro para preservar el comportamiento de reintento. La deduplicación se aplica por emisión, no por par activo/horizonte, y no reescribe registros históricos. Un nuevo cálculo con otro corte puede generar un lote legítimamente distinto.

## Diseño SaaS propuesto

| Entidad | Campos y restricciones propuestas |
|---|---|
| `organizations` | ID interno estable, slug único normalizado, nombre de presentación, estado, fechas de creación/actualización. El slug sirve a navegación y el ID a las relaciones. |
| `organization_memberships` | FK a organización y usuario, clave única compuesta, rol de organización (`owner`, `admin`, `member`, `viewer`), estado y trazabilidad. Proteger la existencia de un propietario activo ante cambios concurrentes. |
| `organization_settings` | FK única a organización, preferencias declarativas y versionadas como zona horaria y moneda, fechas y control de versión para actualizaciones concurrentes. Mantener secretos fuera de este registro. |

El portal público conserva sus rutas. Los espacios privados pueden usar `/org/<slug>/...` en el mismo sitio. En cada solicitud, el servidor resuelve slug, verifica membresía activa y rol vigente, y pasa el ID de organización validado al repositorio. Una sesión de administrador global no concede membresía implícita. No aceptar un `organization_id` de datos del cliente como autorización. Todas las lecturas, mutaciones, búsquedas y exportaciones privadas deben filtrar por organización. Las relaciones entre registros privados deberían usar claves compuestas que impidan cruces entre organizaciones. Las políticas RLS se podrán sumar como defensa en profundidad con contexto de tenant transaccional probado bajo el pool de producción. No depender únicamente de RLS si el rol backend puede eludirla.

Antes de agregar datos empresariales, definir transición aditiva y ownership para cada recurso. Las predicciones personales y las públicas conservan su semántica. La futura escritura empresarial debe definir una clave de idempotencia con alcance explícito de organización. Probar con dos organizaciones, miembros compartidos, usuarios sin membresía, roles revocados y objetos de otro tenant. Verificar tanto los endpoints como consultas directas de repositorio, tareas de fondo, exportaciones y auditoría. Estas entidades todavía no forman parte del esquema.
